## 1. Core Architecture & Concepts

A **GitHub Release** is a packaged distribution milestone grounded in a specific Git tag. It pairs immutable source code with compiled binary assets, checksums, and structured release notes.

```
Git Commit (SHA)  ───►  Git Tag (v1.1.0)  ───►  GitHub Release
                                                    ├── Release Title & Body
                                                    ├── Badges (Latest / Pre-release / Draft)
                                                    └── Distribution Assets (.exe, .blockmap, .yml)
```

### Key Release States & Badges

| Badge / State | Visual | Technical Meaning | When to Use |
| :--- | :--- | :--- | :--- |
| **Latest** | `Latest` (Green pill) | The default production release surfaced at the top of `/releases` and targeted by `/releases/latest`. | General Availability (GA) stable releases. Only one release holds this badge at a time. |
| **Pre-release** | `Pre-release` (Orange pill) | Marked unstable; excluded from default update feeds and the `Latest` pointer. | Alpha, Beta, Release Candidate (`-rc.1`), or nightly channel builds. |
| **Draft** | `Draft` (Gray pill) | Private to repository collaborators with write access; invisible to public users and API queries. | Staging a release while compiling assets across multiple OS runners before public launch. |

## 2. Versioning Discipline (SemVer & Git Tags)

Releases must follow **Semantic Versioning 2.0.0** (`MAJOR.MINOR.PATCH`):

- **`MAJOR`**: Breaking architectural changes, removed APIs, or incompatible config migrations.
- **`MINOR`**: Backward-compatible new features (e.g. adding a new view mode or inspector tab).
- **`PATCH`**: Backward-compatible bug fixes and performance hardening (e.g. clipping fixes).

### Tagging Standards
Always prefix Git tags with `v` (e.g. `v1.1.0`):
```bash
# Annotated, signed tag creation
git tag -a v1.1.0 -m "Release v1.1.0: Modern preview pane & list alignment fixes"

# Push tag to trigger CI release workflow
git push origin v1.1.0
```

> **Warning**: Never use lightweight tags (`git tag v1.1.0` without `-a` or `-s`) for releases. Annotated tags store tagger metadata, timestamps, and GPG signatures necessary for provenance.

## 3. Asset Packaging & Distribution

Release assets are binary distributions compiled for end users. For a production Windows desktop app (e.g. `MyFiles`), a clean release contains:

| Asset | Format | Purpose | Target Audience |
| :--- | :--- | :--- | :--- |
| **Setup Installer** | `MyFiles-Setup-1.1.0.exe` | Standard Windows NSIS installer with start menu shortcuts, uninstaller, and install path selection. | Standard desktop users |
| **Portable Binary** | `MyFiles-Portable-1.1.0.exe` | Standalone executable requiring zero installation; runs from USB drives or temp folders. | Enterprise / Portable users |
| **Blockmap** | `MyFiles-Setup-1.1.0.exe.blockmap` | Differential chunk hash map generated by `electron-builder`. | Differential auto-updater engine |
| **Update Manifest** | `latest.yml` | Metadata containing version, SHA-512 hashes, file size, and release date. | `electron-updater` background worker |
| **Source Code** | `.zip` / `.tar.gz` | Complete snapshot of repo tree at tag commit. | Auto-generated by GitHub |

### Strict Filename Formatting
Avoid spaces or generic names in published binaries. In `package.json`:

```json
{
  "build": {
    "nsis": {
      "artifactName": "${productName}-Setup-${version}.${ext}"
    },
    "portable": {
      "artifactName": "${productName}-Portable-${version}.${ext}"
    }
  }
}
```

This guarantees deterministic artifact filenames across every CI run.

## 4. Auto-Update Infrastructure (Electron & Desktop Apps)

The auto-update workflow relies on `electron-updater` inspecting `latest.yml` on GitHub Releases:

```
[Client App v1.0.0]
       │
       ▼  Checks GitHub Releases (/releases/latest/download/latest.yml)
[latest.yml on GitHub]
       │
       ├─► version: "1.1.0"  (Newer than 1.0.0? Yes)
       │
       ▼  Downloads blockmap (MyFiles-Setup-1.1.0.exe.blockmap)
[Differential Download]
       │
       ├─► Downloads only modified chunks (e.g. 5 MB instead of full 107 MB)
       │
       ▼
[Silent Verification & Background Install]
```

### Format of `latest.yml`
```yaml
version: 1.1.0
files:
  - url: MyFiles-Setup-1.1.0.exe
    sha512: <base64-sha512-hash>
    size: 112197632
    blockMapSize: 118784
path: MyFiles-Setup-1.1.0.exe
sha512: <base64-sha512-hash>
releaseDate: '2026-09-29T10:00:00.000Z'
```

## 5. Release Notes & Changelog Engineering

Release notes communicate changes clearly to users and maintainers.

### Automatic GitHub Release Notes Configuration
Place a `.github/release.yml` in your repository to configure how GitHub categorizes commits into release notes:

```yaml
changelog:
  categories:
    - title: "🚀 Features & Enhancements"
      labels:
        - "feature"
        - "enhancement"
    - title: "🐛 Bug Fixes & UX Polish"
      labels:
        - "bug"
        - "fix"
    - title: "🛡️ Performance & Security Hardening"
      labels:
        - "security"
        - "performance"
    - title: "📦 Build & Packaging"
      labels:
        - "build"
        - "ci"
  exclude:
    labels:
      - "ignore-for-release"
      - "chore"
```

### Manual Release Notes Structure (Recommended Standard)
```markdown
# MyFiles v1.1.0

### Highlights
- High-polish Multi-Selection Inspector with contextual quick actions.
- Liquid Glass optical material depth and specular reflections.
- Aligned List View group headers with native macOS Finder & Windows 11 conventions.

### Fixes & Improvements
- **List View**: Eliminated row clipping and subpixel jitter by standardizing `.view-group-header` as a relative divider.
- **Sidebar**: Pinned drive letters (`(C:)`, `(D:)`) with zero-truncation badges.
- **Navigation**: Isolated scroll restoration to active viewport children.

### Checksums (SHA-256)
| File | SHA-256 |
| :--- | :--- |
| `MyFiles-Setup-1.1.0.exe` | `d97ea9a4f2beaf...` |
| `MyFiles-Portable-1.1.0.exe` | `92e78ea39b4a8c...` |

**Full Changelog**: https://github.com/thesatyamjain/myfiles/compare/v1.0.0...v1.1.0
```

## 6. CI/CD Automation with GitHub Actions

Here is the hardened, production-tested GitHub Actions workflow for building and releasing desktop applications:

```yaml
name: Release

on:
  push:
    tags:
      - 'v*'
  workflow_dispatch:

permissions:
  contents: write

jobs:
  build-release:
    runs-on: windows-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0 # Full history needed for changelog generation

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run verification self-checks
        run: node test/self-check.js

      - name: Clean previous build artifacts
        run: |
          if (Test-Path dist) { Remove-Item -Recurse -Force dist }

      - name: Build Windows Installer & Portable Executable
        run: npx electron-builder --win nsis portable --publish never

      - name: Generate Checksums
        shell: pwsh
        run: |
          Get-ChildItem -Path dist/*.exe | ForEach-Object {
            $hash = (Get-FileHash -Path $_.FullName -Algorithm SHA256).Hash.ToLower()
            "$hash  $($_.Name)" | Out-File -Append -Encoding ascii dist/SHA256SUMS.txt
          }

      - name: Publish to GitHub Releases
        uses: softprops/action-gh-release@v2
        with:
          tag_name: ${{ github.ref_name }}
          name: MyFiles ${{ github.ref_name }}
          draft: false
          prerelease: false
          generate_release_notes: true
          files: |
            dist/*.exe
            dist/latest.yml
            dist/*.blockmap
            dist/SHA256SUMS.txt
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### Critical Rules in this Workflow
1. **Never pass `GH_TOKEN` to `electron-builder` when running `--publish never`**: If `GH_TOKEN` is present, `electron-builder` automatically opens a draft release, resulting in an orphaned draft alongside the release action.
2. **Explicitly specify `dist/latest.yml`**: Never use `dist/*.yml`, which inadvertently matches and uploads `builder-debug.yml`.
3. **Always clean `dist/` before building**: Prevents stale blockmap hashes or old builds from previous steps from being uploaded.

## 7. Incident Runbook & Troubleshooting Common Pitfalls

### Symptom A: Orphaned Draft Release Stuck on Releases Page
- **Cause**: Electron-builder detected a GitHub token during the build step and drafted a release, while `softprops/action-gh-release` published a separate release entry for the same tag.
- **Fix**:
  1. Open the repository on GitHub -> **Releases**.
  2. Locate the release card with the gray **Draft** badge.
  3. Click the **Trash Can icon** (Delete) -> Confirm.
  4. Ensure your workflow does not pass `GH_TOKEN` to `electron-builder` when `--publish never` is used.

### Symptom B: Duplicated "Full Changelog" Lines
- **Cause**: Re-running a GitHub Actions release job when `generate_release_notes: true` is enabled appends another changelog block to the existing release body on every run.
- **Fix**:
  1. Click the **Pencil icon** (Edit release) on the release card.
  2. Remove duplicate changelog markdown lines.
  3. Click **Update release**.

### Symptom C: Internal Debug Files Uploaded (`builder-debug.yml`)
- **Cause**: Workflow file pattern used wildcards (`dist/*.yml`) instead of pinpointing the update manifest.
- **Fix**:
  1. On the release page, click **Edit release** -> click the trash can icon next to `builder-debug.yml`.
  2. In your `.github/workflows/release.yml`, replace `dist/*.yml` with `dist/latest.yml`.

### Symptom D: Mismatched Blockmap Names
- **Cause**: One build produced `MyFiles-Setup-1.1.0.exe.blockmap` (hyphenated) while another produced `MyFiles Setup 1.1.0.exe.blockmap` (spaced).
- **Fix**: Set explicit `artifactName` in `package.json` for both `nsis` and `portable` targets.

## 8. Step-by-Step Guide: GitHub Web (Browser Interface)

The GitHub Web interface provides visual control over releases, draft staging, asset attachments, and changelog generation.

### 8.1 Drafting and Publishing a New Release from Scratch

1. **Navigate to the Releases Section**:
   - Go to your repository home page (e.g. `https://github.com/thesatyamjain/myfiles`).
   - On the right sidebar, click **Releases** (or navigate directly to `https://github.com/<owner>/<repo>/releases`).
2. **Open the Release Form**:
   - Click the black button **`Draft a new release`** in the top-right corner.
3. **Select or Create the Git Tag**:
   - Click the **`Choose a tag`** dropdown menu.
   - If you already pushed a tag from Git or GitHub Desktop: Select it from the list (e.g. `v1.2.0`).
   - If you want GitHub to create the tag upon publish: Type the new tag name (e.g. `v1.2.0`), then click **`+ Create new tag: v1.2.0 on publish`**.
   - Ensure the **Target** branch is set to `main` (or the specific branch/commit SHA you are releasing).
4. **Enter Release Title**:
   - Provide a concise title, typically matching the product name and tag (e.g. `MyFiles v1.2.0`).
5. **Author or Generate Release Notes**:
   - **Automatic Generation**: Click the **`Generate release notes`** button on the top right of the markdown textarea. GitHub will automatically pull all merged pull requests, commit titles, and contributor usernames since the previous release.
   - **Manual Polish**: Review and format sections: `Highlights`, `What's Changed`, `Bug Fixes`, and `SHA-256 Checksums`.
6. **Attach Binary Assets**:
   - Drag and drop your compiled binaries into the box labeled **`Attach binaries by dropping them here or selecting them.`**
   - Required files for desktop release:
     - `MyFiles-Setup-1.2.0.exe` (Windows NSIS Installer)
     - `MyFiles-Portable-1.2.0.exe` (Standalone Portable App)
     - `latest.yml` (Auto-update metadata manifest)
     - `MyFiles-Setup-1.2.0.exe.blockmap` (Differential update blockmap)
   - Wait for each file's progress bar to complete and display its file size (e.g. `107 MB`).
7. **Configure Release Visibility Flags**:
   - **Set as the latest release**: Check this box (checked by default for regular tags) to mark this as the primary production release.
   - **Set as a pre-release**: Check this box if this is an experimental build, alpha, beta, or release candidate (`v1.2.0-rc.1`).
8. **Final Action**:
   - Click the green button **`Publish release`** to make it publicly accessible immediately.
   - OR click **`Save draft`** to store the release privately while assets finish compiling or during final internal verification.

---

### 8.2 Editing an Existing Published Release

1. Navigate to `https://github.com/<owner>/<repo>/releases`.
2. Locate the target release card.
3. In the top-right corner of the release card, click the **Pencil icon** ✏️ (**Edit release**).
4. You can modify:
   - Release Title
   - Tag name or target branch
   - Markdown description/changelog
   - Pre-release / Latest status checkboxes
5. Click the green button **`Update release`** to save your changes.

---

### 8.3 Deleting Unwanted or Leaked Assets from a Release

If an unwanted file (such as `builder-debug.yml` or an outdated blockmap) was uploaded by mistake:

1. Click the **Pencil icon** ✏️ (**Edit release**) on the release card.
2. Scroll down to the **Attach binaries** section.
3. Find the unwanted file in the uploaded assets list.
4. Hover over the file row and click the **Trash Can icon** 🗑️ on the far right of that row.
5. The file will be marked for deletion.
6. Click the green button **`Update release`** at the bottom to finalize the deletion.

---

### 8.4 Deleting an Orphaned Draft Release

When a CI pipeline or script creates a draft release that was never published, it sits at the top of the Releases list with a gray **Draft** badge:

1. Navigate to the Releases page (`/releases`).
2. Locate the release card marked with the gray `Draft` badge.
3. On the top right of the draft card, click the **Trash Can icon** 🗑️.
4. In the confirmation dialog, click **`Delete this draft`**.
5. The draft release is removed instantly. The Git tag and source commits remain untouched.

---

### 8.5 Deleting a Full Published Release

1. Click the **Pencil icon** ✏️ (**Edit release**) on the published release card.
2. Scroll all the way to the bottom of the edit page.
3. Click the red button **`Delete this release`**.
4. Confirm deletion in the pop-up modal.
*(Note: Deleting a release removes the distribution assets and notes, but preserves the underlying Git tag in the repository unless you explicitly delete the tag).*

## 9. Step-by-Step Guide: GitHub Desktop (Desktop App)

GitHub Desktop is a dedicated graphical client for Git version control. While binary asset hosting is managed on GitHub.com, **GitHub Desktop is the fastest and most reliable way to tag releases and trigger automated CI/CD builds without touching the command line.**

```
[GitHub Desktop]                     [GitHub Remote]                   [GitHub Actions]
       │                                    │                                  │
       ├─► 1. Create Tag on Commit          │                                  │
       │                                    │                                  │
       ├─► 2. Push Origin (Push Tag) ──────►│ Tag detected                     │
       │                                    │ ─── on: push: tags: 'v*' ───────►│
       │                                    │                                  ├─► Runs Self-Checks
       │                                    │                                  ├─► Packages Binaries
       │                                    │                                  └─► Publishes Release!
```

### 9.1 Tagging a Release and Triggering CI in GitHub Desktop

1. **Verify Your Changes and Working Tree**:
   - Open **GitHub Desktop**.
   - Ensure you are on the `main` branch (displayed in the top toolbar under **Current Branch**).
   - In the **Changes** tab (left sidebar), verify all release files are committed.
   - Click the top toolbar button **`Fetch origin`** (or **`Pull origin`**) to make sure your local repository is 100% up to date with remote.
2. **Select the Target Commit in History**:
   - Click the **`History`** tab on the left sidebar.
   - The commit history list will appear. Click on the commit you want to release (normally the topmost commit).
3. **Create the Git Release Tag**:
   - Right-click on the selected commit.
   - In the context menu, select **`Create Tag...`**.
   - A modal dialog titled **Create a tag** will appear.
   - In the **Tag name** input box, type the semantic version with the `v` prefix (e.g. `v1.1.0` or `v1.2.0`).
   - Click the blue **`Create Tag`** button.
   - You will now see a blue tag icon with your version label (`v1.2.0`) next to the commit in the History list.
4. **Push the Tag to GitHub Remote**:
   - Look at the top toolbar in GitHub Desktop.
   - The action button now displays: **`Push origin`** with a subtext indicating **`1 tag`** waiting to be pushed.
   - Click **`Push origin`** (or press the keyboard shortcut **`Ctrl + P`**).
   - GitHub Desktop pushes the tag to your GitHub repository.
5. **Monitor the Automated CI Release**:
   - Because `.github/workflows/release.yml` is configured with `on: push: tags: - 'v*'`, GitHub Actions immediately detects the new tag.
   - The runner executes tests (`node test/self-check.js`), compiles the NSIS setup installer and portable executable with `electron-builder`, and publishes the release with all assets automatically.

---

### 9.2 Opening and Inspecting the Release from GitHub Desktop

To quickly jump from GitHub Desktop directly to your release on the web:

1. In GitHub Desktop, press **`Ctrl + Shift + G`** (or go to top menu: **`Repository` -> `View on GitHub`**).
2. Your default web browser will open straight to your repository.
3. Click the **`Releases`** link to view your newly published release and downloaded assets.

---

### 9.3 Deleting or Correcting a Mistaken Tag in GitHub Desktop

If you accidentally tagged the wrong commit or made a typo in the version number:

1. In GitHub Desktop, click the **`History`** tab.
2. Select the commit that contains the tag you wish to delete.
3. Right-click the commit -> select **`Delete Tag <tag-name>...`** (e.g. `Delete Tag v1.2.0...`).
4. A confirmation modal will appear with the option:
   - Check the box: **`Delete from origin`** (to remove it both locally and from GitHub).
5. Click the red button **`Delete Tag`**.
6. The tag is immediately removed, preventing broken or unintentional CI release triggers.

## 10. CLI Management with the GitHub CLI (`gh`)

When maintaining releases from terminal or CI scripts, use the official `gh` CLI:

```bash
# List all releases in repository
gh release list

# View details of a specific release
gh release view v1.1.0

# Create a new release with assets
gh release create v1.1.0 dist/*.exe dist/latest.yml --title "MyFiles v1.1.0" --notes "Release v1.1.0"

# Upload an additional asset to an existing release
gh release upload v1.1.0 dist/SHA256SUMS.txt --clobber

# Delete an unwanted asset from an existing release
gh release delete-asset v1.1.0 builder-debug.yml

# Delete an orphaned release without deleting the Git tag
gh release delete v1.1.0 --cleanup-tag=false
```

## 11. Security, Integrity & Code Signing

### SHA-256 Checksums
Always provide public SHA-256 hashes so enterprise users and package managers (e.g. Winget, Chocolatey, Scoop) can verify file authenticity:

```powershell
# PowerShell command to compute hash:
Get-FileHash -Algorithm SHA256 .\dist\MyFiles-Setup-1.1.0.exe
```

### Git Tag Provenance (GPG Signing)
Sign tags with your GPG key so users can verify that releases originated from an authorized maintainer:
```bash
git tag -s v1.1.0 -m "Release v1.1.0"
git push origin v1.1.0
```

### Code Signing (Windows Authenticode)
Unsigned binaries trigger Windows SmartScreen warnings ("Unknown Publisher"). To eliminate SmartScreen warnings:
1. Acquire an EV (Extended Validation) or OV code-signing certificate (or Azure Trusted Signing).
2. Configure `CSC_LINK` and `CSC_KEY_PASSWORD` in your GitHub repository secrets.
3. `electron-builder` automatically signs the NSIS uninstaller, helper binaries, and final setup executable during CI.
